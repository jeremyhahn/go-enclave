# Plan: release tree check (issue #332)

## Objective

docs/SPEC.md release criterion 8: the release is published as one commit whose
tree is byte-identical to the tag's tree. Nothing checks it. Add
`make release-tree-check TAG=vX.Y.Z REF=<published ref>`, backed by
`scripts/release-tree-check.sh`, so the criterion is a target, not a check by
eye.

The script is offline and read-only. It resolves `TAG^{tree}` and `REF^{tree}`
in the local clone and refuses (non-zero, one line naming both trees) when they
differ, when either does not resolve, or when TAG is not a release version
(`RELEASE_TAG_RE` from `scripts/lib.sh`, the check `release-check-tag.sh`
uses).

## Slices

1. Tests first: `TestScriptsReleaseTreeCheck_*` in
   `build/ci/buildgates/scripts_test.go` on scratch repositories:
   - equal trees pass (REF is a different, squashed commit with the tag's tree);
   - a changed file, a changed mode and an extra file each refuse, naming both
     trees;
   - an unknown TAG or REF refuses;
   - a non-release TAG refuses;
   - the repository is unchanged afterwards.
   They fail on main (the script is missing).
2. The script and the Makefile target with its `## release-tree-check:` help
   line, next to `release-verify` and `consumer-check`.
3. Docs: a row in the Post-tag targets table and a line in the release flow of
   `docs/build-and-release.md`; SPEC criterion 8 links that row; a changelog
   fragment.

## Out of scope

- Fetching the published ref: the caller fetches it first; the script never
  touches the network.
- Wiring the target into the release workflow.
