# Plan: importing go-enclave changes no process state (#342)

## Objective

The backend-detection row in `docs/SPEC.md` and the package documentation in
`harden.go` say that importing go-enclave changes no process state. The
integration suite checks only RLIMIT_CORE
(`TestMemoryEnclave_CoreDumpLimitUnchangedByImport`). This epic checks the
rest of that claim from the kernel's side.

## Slices

1. `TestImport_ChangesNoProcessState` in
   `test/integration/enclave/import_state_test.go`. It runs in an isolated
   child process (the `isolated` helper with default options, so
   `applyChildLimits` changes nothing) whose body calls nothing in go-enclave,
   and asserts:
   - `prctl(PR_GET_DUMPABLE)` is 1;
   - `VmLck` in `/proc/self/status` is 0;
   - `RLIMIT_MEMLOCK` soft and hard equal the devcontainer's declared
     figure (`GO_ENCLAVE_IT_MEMLOCK_BYTES`);
   - `/proc/self/maps` has no `secretmem` mapping.
   Each failure message names the property and says importing must change
   no process state. The test is shown to fail once with a temporary
   `PR_SET_DUMPABLE 0` in the child body (not committed).
2. If the test finds real state change by import: commit the failing test,
   then a fix in the root package.
3. Changelog fragment `changelog.d/342-import-no-state.md`.

## Out of scope

- RLIMIT_CORE, already pinned by
  `TestMemoryEnclave_CoreDumpLimitUnchangedByImport`.
- Process state changed by `HardenProcess` or by constructing an enclave;
  those have their own tests.
