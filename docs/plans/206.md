# Plan: epic #206, arm-trustzone — benchmark harness, vault storage scope

> **Status: REFERENCE** · Scope: go-enclave · Last verified: 2026-11-21

## Objective

The SPEC row arm-trustzone plans material in secure-world RAM behind
trusted-firmware's vault trusted application, with a benchmark recording
open/use/close operations per second and per-access latency. No vault TA
interface is specified anywhere go-enclave can cite: the pinned TA
(`tfw_ta.h`) fixes GET_INFO and GET_RANDOM only. go-enclave designs nothing
in place of an interface trusted-firmware owns, so this epic first ships the
benchmark over the commands that exist and lists what the vault interface
must fix; the vault client follows when trusted-firmware publishes it.

## Slices, in order

1. **Benchmark harness and vault scope (this PR).**
   - `backends/armtrustzone/bench_test.go`: the harness body,
     `benchOpenUseClose` (Connect, one 32-byte Random, Destroy, Close per
     iteration) and `benchAccess` (one session, one 32-byte GET_RANDOM per
     iteration), each reporting `ops/s` and `ns/access`.
     `bench_linux_test.go`: `TestBenchHarness_Fake` runs both once through
     `testing.Benchmark` against the fake TEE, with and without registered
     memory; the fake's cleanup fails on any leaked fd, session or
     shared-memory object.
   - `conformance_optee_test.go`: `BenchmarkOpenUseClose` and
     `BenchmarkAccess` on the OP-TEE endpoint; a missing endpoint fails.
   - `scripts/optee-fixture.sh`: the guest runs the benchmarks after the
     conformance tests; a benchmark failure fails
     `make integration-test-arm-trustzone`.
   - Docs: design doc sections "Vault storage" (open items) and
     "Benchmark"; engineering.md testing paragraph; SPEC row and ROADMAP
     line say what ships. The row stays `in progress`.
2. **Vault client (later, gated on trusted-firmware).** Once the vault TA
   interface is published (UUID, commands, parameters, limits, version and
   flags, errors, lifetime on session close): its text into
   `docs/reference/`, the client, fake-TEE tests, and the vault path in the
   same harness.
3. **i.MX 95 figures (later, gated on hardware).** The harness run on an
   i.MX 95, its figures recorded in the design doc.

## Out of scope

- Any vault command, UUID or parameter layout: none is specified.
- Hardware or i.MX 95 figures: the fixture is OP-TEE on QEMU, and its
  figures are not hardware figures.
- A GlobalPlatform TEE Client API text in `docs/reference/`.
